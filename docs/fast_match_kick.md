# 比赛中优先尽快踢球

2026-10-16：减少本机确认球之后，行为决策到视觉踢球启动请求之间的限制和等待。

前锋持有控球权、本机球源有效、球未出界，且球在 0.05～1.4 米接管范围内并通过粗对准检查时，优先选择 `auto_visual_kick`。最后的朝向和脚位调整交给视觉踢球运控。

原先 1 米以外还要求 `tmMyCost < 7`、球和机器人进入写死的场地区域，以及不满足强力趟球条件。这些重复的战术门槛已移除。满足接管条件时，正在绕球的前锋也在当前决策周期直接交给视觉踢球。

| 参数/行为 | 原值 | 当前值 |
|---|---:|---:|
| 前锋球方位容差 | 0.35 rad（约 20°） | 0.75 rad（约 43°） |
| 前锋接近路线和身体朝向容差 | 各 0.25 rad（约 14°） | 各 0.8 rad（约 46°） |
| 前锋启动前停步等待 | 160 ms | 40 ms |
| 守门员启动前停步等待 | 80 ms | 40 ms |
| 前锋/守门员退出冷却 | 600 ms | 200 ms |
| 启动拒绝或超时后的重试间隔 | 1000 ms | 300 ms |

参数位于 [config.yaml](../src/brain/config/config.yaml)，C++ 参数默认值同步更新。调整节点使用相同的路线容差，避免已经满足接管要求的路线仍反复横移。

控球权、队友让行、有效本机球源、侧后方球先转身、远球先追近，以及比赛暂停/罚时/等待对方开球的行为树检查仍生效。守门员清球区域与方向检查沿用原逻辑。识别置信度门槛没有降低：此次优化发生在识别成功之后。

`real_ball_hold_ms` 是真实观测可沿用的有效期，`min_msec_kick` 是启动后的执行时间，`start_ack_timeout_ms` 是等待运控响应的超时上限；它们都不是启动前必须等待的时间。

本地验证命令：

```powershell
python scripts/test_local.py
```

已通过全部离线策略检查，包括 5 个 C++ 测试程序、7 项行为树检查、普通踢球运行测试和比赛流程运行测试。新增场景直接读取比赛 YAML，并执行提取的生产决策/动作函数，验证左右两侧粗对准、首周期接管、40 ms 启动请求、200 ms 冷却、300 ms 重试、区域/成本不再阻塞，以及球权、队友挡路和球源有效性检查。原有精对准配置的回归场景也继续通过。

40 ms 指行为节点选中后配置的停步等待。实际检测到启动请求还包含行为树调度和通信时间，实际抬脚/触球时间取决于运控和剩余姿态调整。当前验证为离线模拟，尚未完成完整 ROS/Booster 编译或实机部署、计时；需要同步源码和配置后在机器人上重新编译启动，才能评估比赛中的实际收益。
